# Research: the API reference inside the site, and what starts its deployment

The Dokka reference for `shared`, `server` and `web` is generated by the Gradle build and packaged
into the `web` distribution, so the `site` artifact and the server jar both carry it. It is served at
`https://spartanlaboratories.org/docs/api/` and goes through staging and approval with the rest of
the site. The build reads the logo in `docs/brand/` and the stylesheet in `docs/dokka/`, so the site
now depends on files under `docs/`, and `OrganizationPage Deploy` ignores every push that changes
only `docs/`.

Most of what the design needs is settled by this repository, by measurements of the build, or by
findings already on file. One point depends on GitHub's behaviour and has no answer here.

## What existing findings already answer

- How `paths` and `paths-ignore` decide whether a push starts a workflow, how the changed files of a
  merge are worked out, the documented limits, and what a filtered push leaves behind:
  [`../../8-docs-only-deploy-skip/research/github-path-filters.md`](../../8-docs-only-deploy-skip/research/github-path-filters.md).
  It is current: the workflow files it describes are the ones in use. It left one point open that
  matters below: whether `**` matches names that start with a dot.
- How `SamKirkland/FTP-Deploy-Action@v4.4.0` syncs a folder, what its record lists and what it can
  delete: [`../../8-docs-only-deploy-skip/research/ftp-deploy-nested-sync.md`](../../8-docs-only-deploy-skip/research/ftp-deploy-nested-sync.md).
  It is current: the action's version has not moved. The reference is a new folder inside the site's
  own upload, so no nested sync is added.

## Questions

### 1. How should the push trigger of `OrganizationPage Deploy` be written so that a change under `docs/brand/` or `docs/dokka/` starts the deployment, and other changes under `docs/` do not?

`.github/workflows/deploy-spaceship.yml` has `paths-ignore: 'docs/**'` on its `push` trigger, beside
`branches: [main]`. Its comment says to remove or narrow the filter if the site build ever reads
`docs/`. The options worth comparing:

- `paths` with ordered patterns: every path, then `!docs/**`, then `docs/brand/**` and `docs/dokka/**`
  put back;
- `paths-ignore` naming only the parts of `docs/` that do not feed the site (`docs/plans/**`,
  `docs/dashboards/**`, the loose files in `docs/`), so that anything new under `docs/` deploys;
- leaving the filter alone and starting the deployment some other way when the brand files change.

An answer has to establish:

- that a push changing only `docs/brand/` or `docs/dokka/` starts the deployment;
- that a push changing only other files under `docs/`, at any depth, starts none, which is what
  `docs/DEPLOYMENT.md` promises today;
- that a push changing anything outside `docs/` still starts it, **including paths whose names start
  with a dot**, such as `.github/workflows/deploy-spaceship.yml`, `.gitignore` and `.dockerignore`:
  a filter that stopped deploying those would be a regression;
- how GitHub orders and combines positive and negative patterns in `paths`, what happens when a path
  matches both, and whether `paths-ignore` accepts negative patterns at all;
- how `'**'` treats dot-named files and folders at any depth, for each candidate that relies on it;
- which way each option fails when a new folder is later added under `docs/`, given that an extra
  run stops at the production reviewer, and a missed run leaves the reference out of date;
- how the option stays readable and correct alongside `publish-docs.yml`, which stays on
  `paths: docs/**`, so that a push changing both still starts both.

GitHub's workflow syntax documentation settles most of this. Whether `**` crosses dot-named names may
need the implementation or documented test results, because the documentation's silence on it is what
the earlier finding recorded.
